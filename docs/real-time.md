# Real-Time Platform

SentinelRoute treats real-time state as a first-class concern. Every mutation that matters is propagated to all authorized clients without polling.

**Related:** [Architecture](architecture.md) · [Modules](modules.md) · [Deployment](deployment.md) · [Performance](performance.md) · [Back to README](../README.md)

---

## Socket.io Infrastructure

The Socket.io server (`src/lib/socket-server.ts`) is initialized once per Node.js process. It maintains a single namespace and provides typed emit helpers:

- `emitShipmentCreated(shipment)` -called after confirmed MongoDB write
- `emitShipmentUpdated(shipment)` -called after confirmed MongoDB write

The client (`src/hooks/use-socket.ts`) manages a singleton `socket.io-client` instance with `reconnection: true` and `path: "/api/socket"`. Event listeners are registered on mount and removed on unmount via the handler map pattern.

---

## Company Rooms

When a user's connection is established (or re-established), the client emits `join:company` with `companyId`, `userId`, and `role`. The server registers the socket in the company's Socket.io room (`company:{companyId}`). All company-scoped events are broadcast to this room.

Cross-company leakage at the transport layer is structurally impossible -`companyId` is derived server-side from the authenticated user's `UserRecord`, never from client input.

---

## Entity Rooms

Shipment-level collaboration uses entity rooms (`entity:{shipmentId}`). Users viewing a shipment detail page join the entity room, making their presence visible to other viewers of the same shipment.

---

## Presence

Each authenticated user is tracked in the presence map keyed by `userId`. Presence events carry `userId`, `status` (online/offline), `role`, and optional `entityId` for shipment-level presence.

| Event | Description |
|---|---|
| `presence:updated` | A user's presence state changed |
| `presence:entity:joined` | A user joined a shipment entity room |
| `presence:entity:left` | A user left a shipment entity room |
| `presence:sync` | Full presence map sync on reconnect |

The `StoreContext` exposes the `presence` map, enabling the UI to show live collaborators -other users currently viewing the same entity or connected to the same company room.

## Event Channels

| Event | Direction | Description |
|---|---|---|
| `shipment:created` | Server → client | New shipment created and written to MongoDB |
| `shipment:status` | Server → client | Shipment status changed |
| `shipment:updated` | Server → client | Full shipment object updated |
| `feed:updated` | Server → client | Operational feed changed |
| `health:updated` | Server → client | Operational health score changed |
| `kpi:updated` | Server → client | Company KPIs updated |
| `sync:refresh_feed` | Server → client | Trigger client to re-fetch shipments and feed |
| `join:company` | Client → server | Join a company room after connect/reconnect |

## Timeline

The shipment timeline is an append-only, immutable event log. Every operational event -dispatch, status change, weather update, incident detection, recommendation lifecycle transition, driver message, system alert -is written as a `ShipmentTimelineEvent` with:
- `type` -one of 40+ `TimelineEventType` values
- `description` -human-readable event description
- `source` -which system component generated the event
- `confidence` -0–100 confidence score
- `affectedMetrics` -optional list of impacted metrics

The timeline is never edited or deleted.

---

## Messages

Shipment channels support multi-participant messaging:

- **Sender types:** Dispatcher, Driver, Operations Manager, System
- **Message types:** `text`, `system`, `image`, `pdf`
- System messages are auto-generated by workflow transitions (dispatch, risk changes, recommendation lifecycle events)
- Message history is available to all authorized company users

## Store Integration

`StoreContext` (`src/lib/store.tsx`) uses `useReducer`. Socket events dispatch directly to the reducer:

| Socket Event | Reducer Action | Effect |
|---|---|---|
| `shipment:created` | `ADD_SHIPMENT` | Prepend shipment to list (deduplication guard) |
| `shipment:status` | `UPDATE_STATUS` | Replace status on matching `id` |
| `shipment:updated` | `UPDATE_STATUS` | Replace status and lastUpdate |
| `presence:updated` | `PRESENCE_UPDATE` | Merge into presence map |
| `presence:sync` | `PRESENCE_SYNC` | Replace full presence map |
| `feed:updated` | `SET_OPERATIONAL_DATA` | Replace operational feed |
| `health:updated` | `SET_OPERATIONAL_DATA` | Replace health score |
| `kpi:updated` | `KPI_UPDATE` | Replace KPI data |

No optimistic updates. State changes flow exclusively through confirmed server events.

## Polling Fallback

When `NEXT_PUBLIC_ENABLE_WEBSOCKET` is not `"true"` (e.g., on Vercel's serverless runtime), the store activates a 30-second `setInterval` that calls `fetchShipments()` and `fetchOperationalData()`. The interval is cleared on component unmount and user sign-out.

---

## Reconnection Behavior

On reconnect, the client:
1. Re-emits `join:company` to re-enter the company room
2. Calls `fetchShipments()` and `fetchOperationalData()` to recover any missed events
3. Re-registers all socket event handlers

This ensures no events are permanently missed after a connection interruption.

---

## Decision Workspace Sync

Before confirming a dispatch, the dispatcher reviews three route options side by side with risk scores, AI explanations, and any active recommendations. The Decision Workspace receives live recommendation updates via Socket.io so the view reflects the latest operational intelligence at the moment of decision.

---

## Recommendation Sync

When a recommendation is generated, assigned, accepted, or rejected, a Socket.io event propagates the state change to all connected company members. Dispatchers and operations managers always see the current lifecycle status of every recommendation without refreshing.
